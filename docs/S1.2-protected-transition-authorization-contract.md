# S1.2 — Protected Transition Authorization Contract

**Status:** design contract; no runtime behavior changed by this document  
**Scope:** TENIR-Gov durable operation lifecycle, especially HOLD and ESCALATED  
**Parent baseline:** `8a3e0feb56304bf13d7b54216e65d856a97fa730`

## 1. Problem statement

`DurableOperationRegistry.transition_to()` currently enforces the legal state graph and atomicity, but a legal edge does not prove that its lifecycle preconditions were satisfied. A caller can request a legal transition out of HOLD or ESCALATED without passing through the Governor or HoldManager path that is supposed to establish those preconditions.

S1.2 defines the contract for closing that gap. It does not implement the guard and does not claim production authorization or identity verification.

## 2. Normative invariant

A transition out of a holding state MUST NOT succeed solely because the requested target appears in `_LEGAL_TRANSITIONS`.

The registry MUST atomically validate both:
1. the current state and legal target; and
2. a transition authorization whose type, provenance, operation binding, source state, target state, and lifecycle evidence match that transition.

An authorization MUST be rejected if it is absent, invalid, mismatched, already consumed, or used after the operation has changed state. Validation and consumption MUST occur in the same registry critical section as the state transition and durable persistence.

## 3. Protected edges and accepted authorization classes

| Transition | Required authorization class | Minimum precondition |
|---|---|---|
| `HOLD → RESERVED` | `READJUDICATION_ALLOW` | Governor re-adjudicated the same operation with fresh inputs and produced PASS or FLAG; both results map to the allow class for this transition |
| `HOLD → FAILED` | `READJUDICATION_DENY` or `HOLD_EXPIRY` | Fresh Governor re-adjudication produced HARD_VETO, or HoldManager verified τ_K expiry |
| `HOLD → ESCALATED` | `HOLD_ESCALATION` | HoldManager recorded the escalation event and metadata |
| `ESCALATED → RESERVED` | `ESCALATED_AUTHORIZED_APPROVAL` | HoldManager authorized the exit and bound the receipt to the operation and target |
| `ESCALATED → FAILED` | `ESCALATED_AUTHORIZED_DENIAL` | HoldManager authorized denial and bound the receipt to the operation and target |
| `ESCALATED → UNKNOWN` | `ESCALATED_EXPIRY` | HoldManager verified expiry; expiry MUST NOT resolve to an executable state |

**Adjudication mapping:** `PASS` and `FLAG` are the only outcomes that authorize `HOLD → RESERVED`, using `READJUDICATION_ALLOW`. `HARD_VETO` maps to `READJUDICATION_DENY` and may authorize `HOLD → FAILED`; it MUST NOT authorize `HOLD → RESERVED`. `HOLD_EXPIRY` is a separate lifecycle authorization and does not represent an adjudication result. The registry validates the authorization class and transition binding; the Governor is responsible for issuing the class that matches the fresh adjudication result.

Other edges remain governed by the existing legal-transition graph. This contract does not relax or replace the atomic `RESERVED → DISPATCHING` claim, provider-outcome transitions, or UNKNOWN reconciliation.

## 4. Authorization representation

The implementation SHOULD use a typed, opaque, one-use authorization object rather than a boolean, free-form string, caller-supplied reason, or public `authorized=True` flag.

The authorization MUST be bound to:
- the idempotency key;
- the expected source state;
- the requested target state;
- the authorization class;
- the relevant adjudication result or lifecycle receipt;
- a unique nonce or equivalent one-use identifier.

The registry MUST verify provenance through a controlled issuance/verification path. A caller MUST NOT be able to manufacture a valid authorization by constructing an ordinary public data object with matching fields. The capability must not be serializable/replayable as a durable credential; durable evidence may be stored for audit, but it is not itself a live transition capability.

The exact Python API and capability construction mechanism are implementation decisions for S1.3, subject to these constraints.

## 5. Distinguish path enforcement from identity authentication

A registry capability can enforce that a transition passed through the required code path. It does **not**, by itself, authenticate a human, validate a signature, establish organizational authority, or prove that a ceremony took place.

In the current implementation, fields such as `authorized_by`, `scope`, and `authorization` in `ExitReceipt` are plain data. Unless a separately defined organization-owned verifier validates them, they are audit metadata, not cryptographic proof of authority.

S1.3 MUST NOT describe path enforcement as identity or signature verification. Production-grade operator authentication and policy for who may authorize an escalated exit remain separate requirements.

## 6. Atomicity, races, and failure behavior

- Authorization validation, one-use consumption, state mutation, and persistence MUST be atomic with respect to competing threads and processes.
- If the expected source state no longer matches, the transition MUST fail without consuming a capability for a different transition or mutating lifecycle metadata.
- A rejected or stale authorization MUST leave the operation state unchanged.
- Metadata updates (for example, `exit_reason`, escalation fields, or exit receipt) MUST NOT be committed as if a transition succeeded when the state transition fails.
- Repeated use of the same authorization MUST fail.
- Missing or malformed authorization MUST fail closed for protected edges.
- Existing corruption detection and cross-process file-lock behavior MUST remain intact.

## 7. API compatibility and migration

S1.3 SHOULD preserve the existing `transition_to(key, target, claimed_by=...)` shape for unprotected transitions. Protected edges must reject calls that omit the new authorization mechanism; silently inferring authorization from the caller name, target state, or free-form metadata is prohibited.

All production callers must be migrated explicitly:
- Governor re-adjudication issues the appropriate authorization only after composing a fresh result.
- HoldManager issues lifecycle authorizations only after validating the relevant lifecycle precondition.
- Direct callers and tests must be updated to assert that unguarded protected transitions are rejected.
- Test helpers may use an explicit test-only issuer, but production code must not expose a general-purpose bypass.

If a staged migration is required, it must be explicit and temporary; there must be no permissive fallback on the production path.

## 8. Required S1.3 conformance tests

1. Direct `HOLD → RESERVED` without authorization is rejected.
2. Direct `HOLD → FAILED` without an accepted adjudication/expiry authorization is rejected.
3. Direct `HOLD → ESCALATED` without lifecycle authorization is rejected.
4. Direct `ESCALATED → RESERVED/FAILED/UNKNOWN` without the matching authorization class is rejected.
5. An authorization for one operation, source state, or target cannot be reused for another.
6. A capability cannot be replayed after successful consumption.
7. Stale-state and competing-process races cannot use an authorization against a changed state.
8. Governor PASS/FLAG re-adjudication can resolve HOLD to RESERVED; HARD_VETO can resolve it to FAILED.
9. HOLD expiry reaches FAILED only through the expiry path.
10. Escalated authorized approval/denial works through HoldManager; expiry reaches UNKNOWN, never RESERVED.
11. Failed transitions do not leave success-shaped HoldRecord metadata.
12. Existing dispatch atomicity, provider outcome, UNKNOWN reconciliation, recovery, corruption handling, and persistence tests continue to pass.

## 9. Acceptance criteria for S1.2

S1.2 is complete when reviewers agree that:
- the protected edges and authorization classes cover all exits from HOLD/ESCALATED;
- the capability contract closes direct-call and replay paths without replacing the legal state graph;
- authorization is atomic with state mutation;
- path enforcement is clearly distinguished from real-world identity authentication;
- the S1.3 implementation can be tested without weakening dispatch/recovery semantics.

**Out of scope:** implementing the guard, defining organizational signer identities or policies, adding cryptographic signature verification, and claiming production conformance.
